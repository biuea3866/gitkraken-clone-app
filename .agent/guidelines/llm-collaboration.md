# LLM 협업 가이드라인

흔한 LLM 코딩 실수를 줄이기 위한 행동 지침. 프로젝트 고유 규칙과 함께 적용한다.
원문: [karpathy-inspired Claude Code guidelines](https://github.com/multica-ai/andrej-karpathy-skills)
— §1(먼저 읽기)과 실패 모드 표는 커뮤니티 10규칙 파생본에서 선별 채택(유출본 원문은 미검증 루머 — 사실로 인용하지 않고 아이디어만 반영).

**트레이드오프:** 이 가이드라인은 **속도보다 신중함**에 무게를 둔다. 사소한 작업에는 판단을 발휘해 적용 강도를 조절한다.

## 1. 쓰기 전에 먼저 읽기

**코드베이스가 이미 답을 알고 있다. 발명하기 전에 읽는다.**

코드를 작성하기 전에:
- 인접 코드와 유사 구현을 먼저 읽는다 — 새 컨벤션을 발명하지 말고 인접 코드를 따른다.
- 프로젝트가 이미 쓰는 라이브러리·유틸을 확인한다. 같은 일을 하는 새 의존성을 들이지 않는다.
- 기억으로 API를 추측하지 않는다 — 실제 코드·문서를 확인한다.
- 테스트를 추가할 때는 기존 테스트 스타일부터 본다.

## 2. 코딩 전에 먼저 생각하기

**가정하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

구현 시작 전에:
- 가정을 명시적으로 말한다. 불확실하면 묻는다.
- 해석이 여러 개라면 모두 제시한다 — 사일런트로 하나를 고르지 않는다.
- 더 단순한 길이 있으면 말한다. 필요하면 푸시백한다.
- 불명확하면 멈춘다. 무엇이 헷갈리는지 이름 붙이고 묻는다.

## 3. 단순함 우선

**문제를 해결하는 최소 코드. 추측성 요소는 금물.**

- 요청 범위 밖의 기능은 추가하지 않는다.
- 단일 사용처인 코드를 추상화하지 않는다.
- 요청되지 않은 "유연성" 또는 "설정 가능성"을 만들지 않는다.
- 일어날 수 없는 시나리오에 대한 에러 처리는 하지 않는다.
- 200줄을 쓰고 있는데 50줄로 줄일 수 있다면, 다시 작성한다.
- 불필요한 주석은 추가하지 않는다.

자가 점검: "시니어 엔지니어가 이 코드를 보고 과하게 복잡하다고 말할까?" 그렇다면, 단순화한다.

## 4. 외과적 변경

**꼭 손대야 하는 것만 손댄다. 내가 만든 부산물만 정리한다.**

기존 코드를 수정할 때:
- 인접한 코드, 주석, 포맷을 "개선"하지 않는다.
- 망가지지 않은 것을 리팩터링하지 않는다.
- 기존 스타일을 따른다 — 내가 다르게 쓰고 싶더라도.
- 무관한 dead code를 발견하면 **언급은 하되 삭제하지 않는다**.

변경으로 인해 고아 요소(orphans)가 생긴 경우에만:
- **내 변경 때문에** 미사용이 된 import/변수/함수만 제거한다.
- 요청 없이는 기존 dead code를 제거하지 않는다.

테스트: 변경된 모든 줄이 사용자 요청까지 직접 추적 가능해야 한다.

## 5. 목표 주도 실행

**성공 기준을 정의한다. 검증될 때까지 루프를 돈다.**

작업을 검증 가능한 목표로 변환한다:
- "유효성 검사 추가" → "잘못된 입력에 대한 테스트를 작성한 다음, 통과시킨다"
- "버그 수정" → "버그를 재현하는 테스트를 작성한 다음, 통과시킨다"
- "X 리팩터링" → "리팩터링 전후로 테스트가 모두 통과하는지 확인한다"

다단계 작업에는 짧은 계획을 먼저 말한다:
```
1. [단계] → verify: [확인 방법]
2. [단계] → verify: [확인 방법]
3. [단계] → verify: [확인 방법]
```

강한 성공 기준은 LLM이 독립적으로 루프를 돌 수 있게 한다. 약한 기준("동작하게 해줘")은 계속해서 추가 질문을 요구하게 만든다.

## 이름 붙인 실패 모드

아래 패턴이 감지되면 **멈추고, 이름을 붙여 보고한다**. 리뷰·자가 점검에서도 이 이름을 공용 어휘로 쓴다.

| 이름 | 증상 | 위반 원칙 |
|---|---|---|
| Kitchen Sink | 기능 하나 요청에 코드베이스 절반을 재구성 | §3 |
| Wrong Abstraction | 한 곳에서만 필요한 문제에 범용 솔루션 구축 | §3 |
| Invisible Decision | 아키텍처 선택을 알리지 않고 진행 | §2 |
| Optimistic Path | happy path만 처리하고 에러 케이스 무시 | §5 |
| Knowledge Hallucination | 불확실한 API를 자신 있게 사용 | §1 |
| Style Drift | 프로젝트 스타일 대신 개인 선호로 작성 | §4 |
| Runaway Refactor | 수정 하나가 연쇄적으로 여러 파일로 번짐 | §4 |
