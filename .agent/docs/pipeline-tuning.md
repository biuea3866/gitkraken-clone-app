# 파이프라인 튜닝 — 측정과 결정 기록

개발 그래프의 **실행 시간을 줄이되 검증 품질은 깎지 않기 위해** 무엇을 measured 하고 무엇을 바꿨는지 남긴다.
추측으로 조이지 않기 위한 문서다 — 새 조치를 넣을 때는 **측정값을 먼저 붙인다.**

> 이 문서는 "무엇을 바꿨나" 의 기록이고, 규칙 자체의 정본은 아니다.
> 파이프라인 절차는 [`custom-develop-orchestrator`](../skills/custom-develop-orchestrator/SKILL.md),
> 축 정의는 [`custom-self-code-review`](../skills/custom-self-code-review/SKILL.md) 가 정본이다.

## 1. 측정 (wave 2 전량 + wave 3 스펙 단계)

`runs/*/run.json` 의 `duration_s` 집계. 성공 노드만.

| 노드 | 벤더 | n | 중앙값 | 최대 | 성격 |
|---|---|---|---|---|---|
| `repair_and_verify_2` | claude/opus | 5 | **366s** | 391s | 단독 wave — 병렬화 불가, 최장 노드 |
| `evidence` | claude/sonnet | 11 | 127s | 249s | 티켓 간 병렬 가능 |
| `spec` | codex/terra | 11 | 108s | 154s | 티켓 간 병렬 가능 |
| 5축 + 문서 노드 | codex/terra | 각 4~5 | ~100s | 243s | wave 안에서 병렬 — 대기는 wave 당 max |

- **직렬 환산 총계 191분.** 이 중 5축·문서 노드 소계가 106분인데, 병렬이라 **실제 대기는 wave 당 약 240초**다.
- 즉 노드 자체는 이미 병렬화돼 있고, **벽시계를 늘린 것은 노드가 아니라 그 바깥의 실행 방식**이었다.

## 2. 시간을 먹은 원인 3가지 (관측)

### 원인 1 — 티켓 배치를 4개씩 끊었다

티켓 워크트리는 서로 독립인데 wave 3 스펙 11건을 `4 + 4 + 3` 으로 돌렸다.
노드 시간은 같고 벽시계만 3배가 됐다 (**45분 → 15분** 차이).

### 원인 2 — 같은 결함 클래스를 라운드마다 하나씩 잡았다

UND-11 이 대표 사례다. `schemaVersion` 을 해석하지 못하는 **하나의 결함**이 세 라운드에 나뉘어 나왔다.

| 라운드 | 지적 | 실제로는 |
|---|---|---|
| 1 | `Long` → `Int` 절삭으로 2³¹ 이상이 음수로 뒤집힘 | 같은 원인 |
| 2 | 2⁶³ 이상은 파서가 `Double` 을 줘 "버전 없음" 으로 떨어짐 | 같은 원인 |
| 3 | 명시적 `"schemaVersion": null` 이 키 부재와 동일 처리 | 같은 원인 |

라운드당 수정 + 재검증 + 사람 왕복이 붙어 **30분 이상**을 썼다.
셋은 "버전을 해석하지 못하면 보존한다" 는 한 가지 판정의 구멍이며 **한 번에 나왔어야 한다.**

### 원인 3 — 하네스 결함으로 같은 단계를 두 번 돌렸다

`.claude-local/` 은 gitignore 라 새 워크트리에 따라오지 않는데, 노드는 자기 cwd 기준으로 경로를 푼다.
wave 3 스펙 11건이 **요구사항 파일도 결정 문서도 읽지 못한 채** 돌았고 전량 재실행했다 (약 45분).
파일 부재가 **실패가 아니라 침묵**이라 산출물만 보고는 알 수 없었다.

## 3. 적용한 조치

| # | 조치 | 근거 | 품질 영향 |
|---|---|---|---|
| 1 | **배치 금지** — wave 티켓 전부를 한 번에 실행 | 원인 1 | 없음 (워크트리 독립) |
| 2 | **결함 클래스 스윕** — 축 프롬프트 15곳에 "같은 원인의 변형을 전부 묶어 보고" | 원인 2 | **상승** — 한 라운드에 전부 잡는다 |
| 3 | **입력 파일 존재 사전 검증** — 러너가 `--set` 의 경로 값을 실행 전에 확인하고 없으면 중단 | 원인 3 | **상승** — 근거 없는 산출물을 막는다 |
| 4 | **게이트 ⑧ 자동 반복** — `remaining_blocking` 이 남으면 묻지 않고 재검증 (상한 3회) | 원인 2 | 없음 |

### 조치 3 의 동작

```
🛑 --set 으로 넘긴 파일을 찾지 못했습니다 (cwd: <워크트리>):
  requirements_file=.claude-local/UND-13.md
경로는 그래프 cwd 기준입니다. 값이 없다는 뜻이면 파일명 대신 '없음' 을 넘기세요.
```

`.md` · `.json` · `.toml` · `.txt` · `.log` · `.yaml` 로 끝나는 값만 검사하고,
`없음` 같은 자리 채움 값은 검사하지 않는다. 절대 경로는 그대로, 상대 경로는 그래프 cwd 기준으로 푼다.

## 4. 적용하지 않은 것 (품질을 깎기 때문)

| 후보 | 왜 안 하는가 |
|---|---|
| 5축 → 3축 축소 | 이번 세션에서 게이트 ⑧이 잡은 p0 3건·p1 2건이 **전부 "테스트·detekt 통과" 상태**였다. 축을 줄이면 그대로 머지된다 |
| 게이트 ⑧ 생략 | 위와 같음 — 사람이 게이트에서 고친 코드는 어떤 축 노드도 본 적이 없다 |
| 스펙 단계 생략 | 스펙 없이 구현하면 인수 조건이 사후에 만들어진다. 검증이 자기 구현을 기준으로 통과 판정하게 된다 |
| `rollback`·`deploy`·`docs_final` 축을 더 빠른 모델로 | 절감은 wave 당 약 30% 지만 판정 품질이 소폭 떨어진다. **보류** — 시간이 더 급해지면 그때 켠다 |
