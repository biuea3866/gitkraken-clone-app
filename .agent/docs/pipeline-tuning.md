# 파이프라인 튜닝 — 측정과 결정 기록

개발 그래프의 **실행 시간을 줄이되 검증 품질은 깎지 않기 위해** 무엇을 measured 하고 무엇을 바꿨는지 남긴다.
추측으로 조이지 않기 위한 문서다 — 새 조치를 넣을 때는 **측정값을 먼저 붙인다.**

> 이 문서는 "무엇을 바꿨나" 의 기록이고, 규칙 자체의 정본은 아니다.
> 파이프라인 절차는 [`custom-develop-orchestrator`](../skills/custom-develop-orchestrator/SKILL.md),
> 축 정의는 [`custom-self-code-review`](../skills/custom-self-code-review/SKILL.md) 가 정본이다.

## 1. 측정 (wave 2 전량 + wave 3 스펙 단계)

`runs/*/run.json` 의 `duration_s` 집계. 성공 노드만.

| 노드 | 벤더 | n | 중앙값 | 최대 | 성격 |
|---|---|---|---|---|---|
| `repair_and_verify_2` | claude/opus | 5 | **366s** | 391s | 단독 wave — 병렬화 불가, 최장 노드 |
| `evidence` | claude/sonnet | 11 | 127s | 249s | 티켓 간 병렬 가능 |
| `spec` | codex/terra | 11 | 108s | 154s | 티켓 간 병렬 가능 |
| 5축 + 문서 노드 | codex/terra | 각 4~5 | ~100s | 243s | wave 안에서 병렬 — 대기는 wave 당 max |

- **직렬 환산 총계 191분.** 이 중 5축·문서 노드 소계가 106분인데, 병렬이라 **실제 대기는 wave 당 약 240초**다.
- 즉 노드 자체는 이미 병렬화돼 있고, **벽시계를 늘린 것은 노드가 아니라 그 바깥의 실행 방식**이었다.

## 2. 시간을 먹은 원인 (관측)

### 원인 1 — 티켓 배치를 4개씩 끊었다

티켓 워크트리는 서로 독립인데 wave 3 스펙 11건을 `4 + 4 + 3` 으로 돌렸다.
노드 시간은 같고 벽시계만 3배가 됐다 (**45분 → 15분** 차이).

### 원인 2 — 같은 결함 클래스를 라운드마다 하나씩 잡았다

UND-11 이 대표 사례다. `schemaVersion` 을 해석하지 못하는 **하나의 결함**이 세 라운드에 나뉘어 나왔다.

| 라운드 | 지적 | 실제로는 |
|---|---|---|
| 1 | `Long` → `Int` 절삭으로 2³¹ 이상이 음수로 뒤집힘 | 같은 원인 |
| 2 | 2⁶³ 이상은 파서가 `Double` 을 줘 "버전 없음" 으로 떨어짐 | 같은 원인 |
| 3 | 명시적 `"schemaVersion": null` 이 키 부재와 동일 처리 | 같은 원인 |

라운드당 수정 + 재검증 + 사람 왕복이 붙어 **30분 이상**을 썼다.
셋은 "버전을 해석하지 못하면 보존한다" 는 한 가지 판정의 구멍이며 **한 번에 나왔어야 한다.**

### 원인 3 — 하네스 결함으로 같은 단계를 두 번 돌렸다

`.claude-local/` 은 gitignore 라 새 워크트리에 따라오지 않는데, 노드는 자기 cwd 기준으로 경로를 푼다.
wave 3 스펙 11건이 **요구사항 파일도 결정 문서도 읽지 못한 채** 돌았고 전량 재실행했다 (약 45분).
파일 부재가 **실패가 아니라 침묵**이라 산출물만 보고는 알 수 없었다.

## 3. 적용한 조치

| # | 조치 | 근거 | 품질 영향 |
|---|---|---|---|
| 1 | **배치 금지** — wave 티켓 전부를 한 번에 실행 | 원인 1 | 없음 (워크트리 독립) |
| 2 | **결함 클래스 스윕** — 축 프롬프트 15곳에 "같은 원인의 변형을 전부 묶어 보고" | 원인 2 | **상승** — 한 라운드에 전부 잡는다 |
| 3 | **입력 파일 존재 사전 검증** — 러너가 `--set` 의 경로 값을 실행 전에 확인하고 없으면 중단 | 원인 3 | **상승** — 근거 없는 산출물을 막는다 |

## 3-1. 원인 4 — 조치 2 의 부작용 (wave 3 재측정)

조치 2 는 "한 결함의 변형을 전부 찾아라" 를 축 프롬프트 15곳에 넣었다. 라운드 수를 줄이려는
조치였는데 **반대 방향의 부작용**이 있었다: 무엇을 넓힐지에 상한이 없어, 축이 **이번 diff 가 만들지
않은 인접 기존 코드**까지 같은 부류로 넓혀 차단했다.

wave 3 관측 (UND-21, `develop-4-verify` 5라운드):

| 라운드 | 지적 | 성격 |
|---|---|---|
| 1 | skip 에 확인 토큰 없음 | 원래 결함 — 수정 |
| 2 | Gateway 메서드가 토큰 없이 public · 확인-실행 비원자성 | 인접 확장 — 수정 |
| 3 | `abortMerge` 가 임계구역에서 상태 미검증 | 인접 확장 — 수정 |
| 4 | `continue*` 도 같은 가드 필요 · 테스트에 단정 추가 | 인접 확장 — 수정 |
| 5 | `rememberStartPoint`(이 티켓이 만들지 않음) · 주석 문자열 오탐 | **확장 + 오탐 — 중단** |

라운드마다 개별로는 타당했지만 **차단이 줄지 않았다.** 다른 티켓도 같은 양상이었다:
UND-19 는 경로 기반 TOCTOU 완전 제거(플랫폼이 제공하지 않는 보장)를 요구했고, UND-13 은 결정문
A1 이 승인한 소유 범위를 재론했고, UND-16 은 자기 오케스트레이션 산출물을 finding 대상으로 삼았다.

**조치**: [`review-grading.md`](./review-grading.md) "차단 판정의 전제" 를 두고, 축 프롬프트
15곳의 확장 지시에 그 경계를 **같은 문단으로** 짝지웠다 (멀리 있는 규칙은 가까운 강조 지시에
밀린다). 요약 노드 3곳에는 백스톱을 뒀다. 심각도는 유지하고 차단만 뗀다 — 기존 p0 를 p4 로
낮추면 후속 티켓에서 위험을 잃는다.

### 정정 — 원인 4 의 진단이 부분적으로 틀렸다

replay 로 검증하면서 위 표의 UND-21 사례 판단이 **오판**이었음이 드러났다.
라운드 5 의 `rememberStartPoint` 를 "이 티켓이 만들지 않은 기존 코드" 로 봤는데,
`git show --name-status` 결과 `MergeGatewayImpl.kt` 는 UND-21 이 **추가한 신규 파일(`A`)** 이다.
축 노드가 옳았고 그 p1 은 이 티켓의 결함이었다 (후속 UND-54 로 남겼다).

따라서 **UND-21 의 라운드가 길었던 것은 루프 고장이 아니다.** 서브시스템 하나를 통째로 신설한
티켓이라 경화 표면이 넓었고, 라운드마다 그 신규 코드의 다른 구멍이 나왔다. 재검증이 실제로
기능한 증거도 있다 — replay 에서 오탐 1건이 사라지고 중복 2건이 1건으로 병합됐다.

이 정정에 따라:
- **C1 을 기계적 판정으로 좁혔다** — 신규 추가 파일(`A`)의 내용은 C1 대상이 아니다. 이 조건이
  있었다면 위 오판이 애초에 불가능하다.
- **C3(닫힌 부류 재개 금지)을 철회했다** — 그 규칙이 작동했다면 UND-21 의 미완 상태 가드를
  통과시켰을 것이다. 미완 경화를 숨기는 규칙은 라운드를 아끼는 대신 결함을 내보낸다.
- C2·C4·C5 는 각각 확인된 사례가 있어 유지한다 (UND-19 TOCTOU · UND-13 결정문 재론 · UND-16 산출물 참조).

### 조치 3 의 동작

```
🛑 --set 으로 넘긴 파일을 찾지 못했습니다 (cwd: <워크트리>):
  requirements_file=.claude-local/UND-13.md
경로는 그래프 cwd 기준입니다. 값이 없다는 뜻이면 파일명 대신 '없음' 을 넘기세요.
```

`.md` · `.json` · `.toml` · `.txt` · `.log` · `.yaml` 로 끝나는 값만 검사하고,
`없음` 같은 자리 채움 값은 검사하지 않는다. 절대 경로는 그대로, 상대 경로는 그래프 cwd 기준으로 푼다.

## 4. 적용하지 않은 것 (품질을 깎기 때문)

| 후보 | 왜 안 하는가 |
|---|---|
| 5축 → 3축 축소 | 이번 세션에서 게이트 ⑧이 잡은 p0 3건·p1 2건이 **전부 "테스트·detekt 통과" 상태**였다. 축을 줄이면 그대로 머지된다 |
| 게이트 ⑧ 생략 | 위와 같음 — 사람이 게이트에서 고친 코드는 어떤 축 노드도 본 적이 없다 |
| 스펙 단계 생략 | 스펙 없이 구현하면 인수 조건이 사후에 만들어진다. 검증이 자기 구현을 기준으로 통과 판정하게 된다 |
| `rollback`·`deploy`·`docs_final` 축을 더 빠른 모델로 | 절감은 wave 당 약 30% 지만 판정 품질이 소폭 떨어진다. **보류** — 시간이 더 급해지면 그때 켠다 |

## 5. 다음에 측정할 것

- 조치 2 적용 후 **티켓당 수정 라운드 수**가 실제로 줄었는지 (기준선: UND-11 4회 · UND-08 3회 · UND-06 2회)
- 조치 1 적용 후 wave 3 구현 단계의 **벽시계 대 노드 시간 비율**
- `repair_and_verify_2`(366s, 최장 단독 노드)를 쪼갤 수 있는지 — 수정과 재빌드를 분리하면 재빌드만 재실행 가능
- **조치 5 가 실제로 강등을 만드는지** — replay(UND-21) 에서는 `advisory` 0건이었다. C1 을 좁힌
  뒤이므로 wave 4 에서 `non_blocking_reason` 이 한 번도 안 붙으면 **규칙이 불필요하다는 신호**로 읽고
  걷어낸다. 규칙을 남겨 두는 비용은 프롬프트 길이와 오강등 위험이다
- 라운드 수 자체는 지표로 쓰지 않는다 — 신규 서브시스템 티켓은 표면이 넓어 라운드가 길 수 있고,
  그것은 정상이다 (위 정정)
- **`advisory` 의 `non_blocking_reason` 분포** — C1 이 압도적이면 경계가 맞는 것이고, C3·C6 이 많으면
  축 프롬프트의 확장 지시를 더 좁혀야 한다는 신호다
