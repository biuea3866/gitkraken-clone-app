# 리뷰 등급 (p0~p5) 과 verdict — in-repo 정본

코드 리뷰 지적의 심각도 등급과 verdict 산출 규칙. `.agent/orchestration/workflows/develop-*.toml`
의 리뷰 노드, `.agent/skills/custom-self-code-review`, `.agent/skills/custom-pr-review` 가
**같은 기준**을 쓰도록 여기에 단일 정의를 둔다 (clone 단독 동작 — 개인 글로벌 설정에 의존하지 않는다).

## 등급

| 레벨 | 기준 | verdict 영향 |
|---|---|---|
| **p0** | 보안 취약점 · 데이터 손실 · 크래시 · 인증/인가 우회 | REQUEST_CHANGES |
| **p1** | 레이어 의존 위반 · 컨벤션 위반(`.agent/rules/`) · 프로세스 게이트 위반(`.agent/docs/conventions.md`) · 설계-코드 불일치 | REQUEST_CHANGES |
| **p2** | 신규 비즈니스 로직에 테스트 없음 · 과대 메서드 · 변수명 축약 · 조용한 실패(예외 삼킴·부적절한 fallback) | REQUEST_CHANGES |
| **p3** | 네이밍 nit · 포맷 · 사소한 가독성 개선 | COMMENT |
| **p4** | 대안 제안 (현재 코드도 무방) | COMMENT |
| **p5** | 정보성 코멘트 (액션 불필요) | — |

## verdict 산출

```
p0~p2 가 하나라도 있으면        → REQUEST_CHANGES
p3~p4 만 있으면                 → COMMENT
p0~p4 가 없으면                 → APPROVED
```

`.agent/orchestration/schemas/review.json` 의 `verdict` enum 이 이 규칙의 기계 표현이다.

## 판정 규율 (모든 리뷰 주체 공통)

1. **변경 파일 전수 읽기.** 요약·추측으로 판정하지 않는다.
2. **근거 필수.** 모든 finding 에 `파일:라인` 과 구체 패턴을 적는다. "위험해 보임" 류 금지.
3. **오탐 SSOT 선행 대조.** finding 을 적기 전에 [`review-false-positives.md`](./review-false-positives.md)
   를 읽고, 해당하는 패턴이면 기각 또는 강등한다 (diff 밖 단정 · nullable 자체 지적 ·
   soft-delete/`@TransactionalEventListener(AFTER_COMMIT)`/`PESSIMISTIC_WRITE` 같은 의도된 컨벤션).
4. **컨텍스트를 읽었다면 상향.** 스펙·티켓 AC 를 읽은 상태에서 발견한 코드-설계 불일치는 p1 이상이다.
5. **자동 수정 대상은 p0~p2 뿐.** p3~p4 는 보고에 남기고 자동으로 고치지 않는다 (스코프 확산 방지).

## 차단 판정의 전제 — diff 인과성 (수렴 규칙)

**등급과 차단은 다르다.** p0~p2 라는 등급은 "얼마나 심각한가" 이고, verdict 차단은 "이 티켓이
그것 때문에 못 나가는가" 다. 남의 결함으로 이 티켓을 영구히 막지 않으려면 둘을 나눠야 한다.

**다만 이 규칙은 차단을 없애는 힘이 있으므로 좁게 쓴다.** 자격 판정이 느슨하면 진짜 회귀가
`advisory` 로 빠져 그대로 머지된다 — 그것이 검증을 길게 도는 것보다 나쁘다. 아래 전제는
**기계적으로 확인 가능할 때만** 적용하고, 애매하면 차단으로 둔다.

자격이 없으면 등급(심각도)은 그대로 매기되 `findings` 가 아니라 **`advisory`** 에 넣고,
`non_blocking_reason` 과 (C1·C2 면) 후속 티켓 내용을 적는다.

| # | 전제 | 적용 조건 (이걸 못 보이면 차단 유지) |
|---|---|---|
| C1 | **기존 결함이다** — 이번 diff 가 만들지 않았다. | `git diff --name-status <merge-base> HEAD` 에서 그 파일이 `A`(신규)가 **아니고**, 지적된 심볼·라인이 merge-base 에 이미 존재함을 확인해 근거로 적는다. **신규 추가 파일의 내용은 C1 대상이 아니다** — 파일 전체가 이번 diff 의 산물이다 |
| C2 | **고칠 수 없다** — 이 언어·플랫폼·이 티켓이 소유한 계약 안에서 달성 불가하다. | 무엇이 있어야 가능한지 적는다 (예: 경로 기반 TOCTOU 완전 제거는 fd 를 보유하는 `openat` 계열이 필요하고 JDK 가 이식성 있게 노출하지 않는다). "어렵다" 는 사유가 아니다 |
| C4 | **결정 문서가 정했다.** | 근거 결정 항목을 인용한다 (`.claude-local/*-DECISIONS.md` 의 절·번호) |
| C5 | **리뷰 대상이 아니다** — 오케스트레이션 산출물(`.agent/orchestration/runs/**`)은 프로세스 상태다. | 해당 경로임을 적는다 |

> **C3 은 철회됐다 (결번).** "어떤 결함 부류의 이 diff 안 사례가 모두 처리됐으면 그 부류를 닫는다"
> 는 규칙을 뒀었는데, 실제로는 **미완 경화를 숨긴다**. UND-21 에서 상태 가드 부류는 닫히지
> 않았고(시작 경로가 남아 있었다) C3 이 작동했다면 그 p1 을 통과시켰을 것이다. 부류가 정말 닫혔다면
> 축이 새 사례를 못 찾으므로 규칙이 필요하지 않다. ID 는 재사용하지 않는다.

### 테스트 지적의 경계 (C6)

테스트 finding 은 **이 diff 가 만든 동작 중 검증되지 않은 것**을 지목해야 p2 다.
이미 테스트가 있는 동작에 단정을 더 붙이라는 요구는 **p3** 이며 차단하지 않는다 —
그 요구는 라운드마다 무한히 깊어질 수 있다. 단, 그 동작의 **실패·경계 입력이 아예 없다면**
그것은 "검증되지 않은 동작" 이므로 p2 가 맞다.

### 관측 근거와 그 한계 (정직한 기록)

이 규칙은 wave 3 재검증(UND-21 5라운드 등)을 계기로 만들었다. 각 전제의 근거 강도는 다르다.

| 전제 | 근거 | 강도 |
|---|---|---|
| C2 | UND-19 가 경로 기반 TOCTOU 완전 제거를 요구했다 — Java NIO 로 달성 불가 | **확인됨** |
| C4 | UND-13 이 결정문 A1 이 승인한 `application/sidebar` 소유 범위를 재론했다 (결정문에 기각 기록까지 있다) | **확인됨** |
| C5 | UND-16 이 자기 `deploy_2.json` 을 finding 대상으로 삼았다 | **확인됨** |
| C1 | **근거가 무너졌다.** UND-21 의 `rememberStartPoint` 를 "기존 코드" 로 본 것은 오판이었다 — `MergeGatewayImpl.kt` 는 그 티켓이 추가한 신규 파일(`A`)이다. 축 노드가 옳았다 | **미확인** — 그래서 위 적용 조건을 기계적 판정으로 좁혔다 |
| C6 | UND-21 라운드 4→5 의 단정 추가 요구 | 약함 (한 사례) |

**UND-21 의 라운드가 길었던 실제 이유는 루프 고장이 아니다.** 그 티켓이 서브시스템 하나를
통째로 신설해 경화 표면이 넓었고, 라운드마다 그 신규 코드의 다른 구멍이 나온 것이다.
재검증이 실제로 잡은 것도 있다 — replay 에서 오탐 1건이 사라지고 중복 2건이 1건으로 병합됐다.

> **수렴 관찰**: 라운드가 진행될수록 차단은 줄어드는 것이 정상이다. 늘어난다면 요약 노드가
> `summary_ko` 에 **왜 늘었는지**(새 회귀인가, 신규 코드의 다른 구멍인가)를 적는다.
> 늘었다는 사실만으로 자동 강등하지 않는다 — 그것이 C3 이 틀린 이유다.

## 판정 불가 시 (fail-closed)

리뷰 산출물이 없거나 파싱 실패(`_parse_error`)거나 `verdict` 키가 없으면 **REQUEST_CHANGES 로
취급**한다. 판정 불가를 통과로 읽으면 검증을 건너뛴 채 사람 게이트에 도달한다.

**이 규칙은 `verdict` 를 선언하는 스키마의 산출물에만 적용된다** — `review.json` ·
`final-summary.json` · `ticket-review.json` 이다. **축 산출물(`axis-review.json`)에는 `verdict`
필드가 없다**: 축은 판정을 내리지 않고 `findings` 를 올리며, 판정은 그것을 모으는 요약 노드가 한다.
축 산출물에 `verdict` 가 없다는 것을 fail-closed 사유로 올리지 않는다 — 스키마가 그렇게 정의돼 있어
**모든 축이 영구히 걸리고**, 코드에 지적이 없는 티켓도 APPROVED 에 도달할 수 없다.
축의 판정 불가는 파일 부재 또는 `_parse_error` 로만 판단한다.
