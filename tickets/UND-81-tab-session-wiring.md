# [UND-81] 탭 세션 배선 — 다중 저장소와 Undo 범위를 잇는다

> wave 9 · 사이즈 L · 의존 UND-43 · UND-44 · UND-51 · UND-80 · 소유 `presentation/RepositorySessionDriver.kt` · `di/AppComponent.kt`(세션 범위) · `presentation/App.kt`(탭 슬롯)

## 작업 내용 (설계 의도)

UND-44 가 만든 다중 저장소 세션과 UND-43 의 Undo 스택을 앱에 잇는다. **UND-51 에서 분리했다** —
그 티켓의 수리 4회전이 낸 새 결함이 **전부 이 영역**이었고, 한 티켓에서 화면 배선과 함께 풀려니
수정할 때마다 다른 쪽이 깨졌다.

### UND-51 이 남긴 결함 (이 티켓이 푼다)

| 결함 | 내용 |
|---|---|
| Undo 이력 소실 (p0) | 조회 실패로 `clearContext()` 가 활성 탭의 undo 범위를 null 로 만들면, 탭은 남아도 그 저장소의 이력이 사라진다 |
| 락 소유 위치 (p1) | presentation 이 자기 `Mutex` 로 전이를 직렬화한다 — 결정 **C2** 는 "동기화는 홀더가 소유하고 소비자가 자기 락을 갖지 않는다" 로 정했다 |
| 원자성 (p1) | `COMMIT_TO_PARENT` 배선이 stage 와 commit 을 별도 호출한다. 사이에 취소되면 gitlink 만 index 에 남는다 |

### 설계 지점

1. **직렬화를 홀더로 옮긴다.** UND-44 가 `GitAccess.withSessions { }` 로 세션 전이를 한 임계 구역에
   묶었다. 표시 상태(탭 목록·셸 선택·컨텍스트) 전이도 **같은 구역 안에서** 끝나야 한다 — presentation 이
   별도 락을 갖는 지금 구조는 두 락이 서로를 모르는 상태다.
2. **Undo 범위의 수명을 탭 수명에 맞춘다.** 조회 실패는 범위를 지우는 사유가 아니다 (결정 G25 와 같은
   원칙 — 일시적 오류로 사용자의 것을 지우지 않는다). 범위는 **탭이 닫힐 때** 사라진다.
3. **화면이 요구한 복합 동작은 한 단위로 실행한다.** `COMMIT_TO_PARENT` 처럼 두 연산이 묶인 것은
   중간 상태를 남기지 않는다.

**UND-80 선행**: 변경 실행이 시작 시점 세션에 묶이지 않으면 이 티켓의 범위 분리도 반쪽이다 —
기록은 A 범위에, 변경은 B 저장소에 갈 수 있다. UND-80 이 먼저 서야 한다.

**롤백**: 배선이라 revert 로 되돌아간다. 되돌리면 탭 전환이 동작하지 않으므로 UND-51 의 단일 저장소
경로가 남아 있어야 한다.

## 테스트 케이스

- 탭 전환 후 화면이 그 탭의 저장소를 참조한다 (저장소마다 표식 브랜치로 확인)
- 빠르게 전환해도 셸 선택과 컨텍스트가 같은 저장소를 가리킨다
- 조회가 실패해도 탭과 그 저장소의 Undo 이력이 남는다
- 탭을 닫으면 그 탭의 Undo 범위가 사라지고 다른 탭 이력은 그대로다
- 같은 브랜치·HEAD 인 clone 둘을 열어도 A 의 기록이 B 이력에 보이지 않는다
- presentation 이 자기 락을 갖지 않는다 (정적 검사 또는 구조 테스트)
- `COMMIT_TO_PARENT` 가 중간에 취소되면 index 에 gitlink 만 남지 않는다
